# TPL: the template itself

The rows that keep this template honest. A project created from it keeps these and adds its own
area files beside them.

| ID | Requirement | Status |
|---|---|---|
| TPL-1 | Every file in `agents/` has frontmatter with `name`, `description`, `tier`, `access`, `skills` and `hands_off_to`, its `name` matches the file name, `tier` is deep, standard or fast, and `access` lists only read, web, run, edit and delegate, with delegate on the orchestrator alone. | T |
| TPL-2 | Every skill an agent lists exists in `skills/`, and every agent named in `hands_off_to` exists in `agents/`. | T |
| TPL-3 | Every folder in `skills/` has a `SKILL.md` whose `name` matches the folder and whose `description` says when to use it. | T |
| TPL-4 | The team table in `AGENTS.md` lists every agent in `agents/` and no other, each with a one-line job and a link to its own file, and `project.toml [team] enabled` names only agents that exist. | T |
| TPL-5 | `AGENTS.md`, each agent file and each `SKILL.md` stay inside their size budgets, so loading them stays cheap. | T |
| TPL-6 | The tool files generated by `tools/sync_adapters.py` match their sources in `agents/` and `skills/`; a hand edit to a generated file fails the sweep. | T |
| TPL-7 | The commit-msg hook refuses the characters banned in `project.toml [style]`, with either line ending, and accepts any other message, including co-author trailers, tool bylines and session links. | T |
| TPL-8 | No tracked text file contains a character banned in `project.toml [style]`. | T |
| TPL-9 | Requirement rows are well formed, ids are unique, status letters are T, M, U, X or n/a, every T row is named by a check, and every id cited in a check exists. | T |
| TPL-10 | The row counts in `docs/REQUIREMENTS.md` are computed by `tools/checks/req_check.py --fix`, never typed. | T |
| TPL-11 | Every running or planned entry in `docs/EXPERIMENTS.md` has a hypothesis, a prediction, a "wrong if" and a read date. | T |
| TPL-12 | Every region pack in `docs/legal/regions/` opens with the not-legal-advice line and carries an "As of" date and a sources list. | T |
| TPL-13 | `tools/run_all.py` exits 0 when green, 2 when every failing line is registered in `tools/known_red.json`, and 1 on a new red, an overdue recheck or a broken check. | T |
| TPL-14 | (A-1) The setup interview writes `project.toml`, the region packs and the first decisions, and leaves the sweep green. | M |
| TPL-15 | (A-2 to A-5) The template works from Claude Code, Codex, Gemini CLI and Cursor: each reads `AGENTS.md`, and the native agents and skills are generated where the tool supports them. | U |
| TPL-16 | Every open assumption in `docs/ASSUMPTIONS.md` has a way to confirm it and a confirm-by date that has not passed, and every settled one says what settled it. | T |
| TPL-17 | Text copied verbatim from upstream (the Karpathy guidelines, Anthropic's frontend-design skill) stays unchanged, pinned by hash in `tools/lib/verbatim.py`, so it can be compared with upstream. | T |
| TPL-18 | The README opens with the premise, building a software startup without writing code, says plainly that this is not vibe coding, and shows each step of the workflow beside the established software practice it follows. | M |
| TPL-19 | The README shows the template's architecture as a diagram (the founder, the AI tool, the instructions it reads, the files it writes and the checks it runs), and every diagram in `docs/images/` reads in both light and dark themes. | M |
| TPL-20 | The template has a landing page built from `site/` and published to GitHub Pages by `.github/workflows/pages.yml`, which copies the diagrams from `docs/images/` at build time, and a 1280 by 640 social preview image rendered from `docs/images/social-preview.svg`. | M |
| TPL-21 | `docs/images/demo.svg` replays the recorded setup dry run with every line quoted word for word from its transcript, and any still frame of it shows the whole exchange. | M |
| TPL-22 | For every feature and bet, `researcher` writes `docs/work/<id>/research.md` before the first grilling round: five to eight similar products, each with what it does, its price and a dated source, and suggestions that the grilling puts to the founder as options with a recommendation. | U |
| TPL-23 | For every feature and bet, `feasibility` writes `docs/work/<id>/feasibility.md` after grilling and before the founder confirms the spec: a go, go with changes or no-go verdict, each part's risk with a dated source, running cost at 1x and 10x usage, and the blockers. Recommended changes go back to the founder. | U |
| TPL-24 | `reviewer` reviews each spec, design and developer diff before it is handed on and writes `docs/work/<id>/review.md` with blocking findings and suggestions; it never edits the work, and nothing moves on while a blocking finding is open unless the founder accepts it in writing. | U |
| TPL-25 | `dashboard` builds a private, sign-in only dashboard for the founder with each figure traced to one source; for a product that calls AI or another paid service, it shows usage and spend per user, per feature and in total against the caps and the budget, and offers the founder's chosen controls, each confirmed, audited and reversible. | U |
| TPL-26 | The project manager is the founder's single point of entry: `AGENTS.md` makes every session answer as `orchestrator`, which starts setup by itself on a new project (after checking Git and Python), and no guide asks the founder to type a command or name an agent. | M |
| TPL-27 | `docs/START-HERE.md` takes a non-technical founder from nothing to the first message to the project manager with Claude Code in a terminal, typing only the install line and `claude`, with real screenshots in `docs/images/start/`, and is linked first from the README and the landing page. | M |
